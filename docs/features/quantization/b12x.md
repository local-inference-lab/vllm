# b12x Backends

[b12x](https://pypi.org/project/b12x/) provides optional CUDA kernels for
NVIDIA SM120 and SM121 GPUs. Install the dependency with:

```bash
uv pip install "vllm[b12x]"
```

b12x linear kernels participate in automatic selection after established
optimized backends and before emulation. Select the linear and MoE backends
explicitly with:

```bash
vllm serve <model> \
    --linear-backend b12x \
    --moe-backend b12x
```

Only pass `--moe-backend b12x` for a compatible NVFP4, MXFP4, IQ2_XS, IQ2_XXS,
or Q8_0 MoE model. The linear and MoE backends can be selected independently.

## Dense activation precision

With `--linear-backend b12x`, eligible BF16-input NVFP4 and MXFP8 layers use
`b12x.gemm.blockscaled.mm(..., mode="auto")` on SM120/SM121. b12x selects
quantized activations or BF16 activations with inline weight dequantization
using the live GEMM row count and static weight geometry. Matching measured
profiles take precedence over its geometry heuristic. vLLM passes the original
activation: quantization, when selected, runs inside b12x. Both routes share
the packed weight, block scales, and weight global scale.

Set these variables before loading the model:

| Variable | Default | Values |
| -------- | ------- | ------ |
| `VLLM_B12X_DENSE_ACTIVATION_MODE` | `auto` | `auto`, `a16`, `quantized` |
| `VLLM_B12X_NVFP4_ACTIVATION_MODE` | Inherit common setting | `auto`, `a16`, `quantized` |
| `VLLM_B12X_MXFP8_ACTIVATION_MODE` | Inherit common setting | `auto`, `a16`, `quantized` |

A recipe override takes precedence even when explicitly set to `auto`.
`a16` forces BF16 activations; `quantized` forces W4A4 or W8A8. Explicit A16
requires BF16 input, K divisible by 128, and N divisible by 8 in this integration;
an unsupported request raises an error. FP16 inputs and other weight formats
retain their existing execution paths. These settings apply only to dense
NVFP4/MXFP8 layers; they do not control MoE, integer INT4/INT8, MXFP4, or
tensor/128x128-block FP8 layers.

For example, force W4A16 while retaining automatic MXFP8 selection:

```bash
VLLM_B12X_NVFP4_ACTIVATION_MODE=a16 \
vllm serve <model> --linear-backend b12x --dtype bfloat16
```

The b12x policy setting `B12X_POLICY_MODE=heuristic-only` bypasses measured
profiles; `auto` is its default. `preplanned-only` requires profile coverage.
Warmup exercises the selected precision at each serving/capture size before
CUDA graph capture. Replay retains its captured precision route and allocations.

This integration requires a b12x source build containing dense activation
precision selection and SM121 support, plus CUDA 13.3 for packed BF16
conversions. The published `b12x==1.3.0` dependency alone does not contain those
changes. Install the corresponding source checkout into the vLLM environment:

```bash
uv pip install --python .venv/bin/python --no-deps -e /path/to/b12x
```

## MoE activation precision

b12x uses MXFP8 activations by default for MXFP4 MoE and the checkpoint's
activation format for NVFP4 MoE. MXFP4 falls back to BF16 when its A8 path does
not support the model configuration. Set `VLLM_B12X_MOE_FP4_FORCE_A16=1` to
force BF16 activations for either FP4 weight format.

For NVFP4 MoE, activation scales remain per expert by default. Set
`VLLM_B12X_MOE_FP4_LAYER_MAX_INPUT_SCALE=w13` to use the layer maximum for the
fused gate/up projection, or set it to `w2` for the down projection. Use `all`
or `1` to enable both independently; `0` disables both.

## Supported Configurations

| Backend | Supported configurations |
| ------- | ------------------------ |
| Linear | Per-tensor FP8, 128x128 block FP8, MXFP8, NVFP4, MXFP4, IQ2_XS, IQ2_XXS, and Q8_0 |
| MoE | Tensor-parallel MXFP4 weights with BF16 or MXFP8 activations; NVFP4 weights with BF16, NVFP4, or MXFP8 activations; EXL3, IQ2_XS, IQ2_XXS, or Q8_0 weights with BF16 activations |

ModelOpt W4A16 NVFP4 checkpoints use BF16 activations without activation scales.
Dense NVFP4 activation promotion uses the W4A4 checkpoint contract described
above. The b12x MoE backend does not support expert parallelism, expert maps,
or NF3.

## IQ2_XS, IQ2_XXS, and Q8_0 safetensors

Status: implemented for ModelOpt mixed-precision checkpoints with IQ2_XS routed
experts and dense layers, including shared experts, alongside independently
configured NVFP4 layers. This path requires a b12x source build with
`IQ2XSWeights`, `IQ2XSLinearWeight`, and IQ2_XS A16 kernels; it does not load
GGUF containers.

Each IQ2_XS recipe must specify `group_size=256`, `block_payload_bytes=74`, and
`packing="ggml"`. Per-expert gate, up, and down tensors are `uint8` arrays with
shape `[N, K/256, 74]`. Loading preserves the packed bytes and applies aligned
tensor-parallel slices. Preparation losslessly rearranges the blocks into compact
b12x storage and releases the source tensors. Weights are decoded inside the
W4A16 kernels; there is no resident BF16 expansion.

Routed experts require BF16 activations, bias-free gated SiLU or non-gated
ReLU-squared, and hidden and per-rank intermediate dimensions divisible by 256.
Dense layers require BF16 activations, a per-rank input dimension divisible by
256, and a per-rank output dimension divisible by 8. Dense plans use the b12x
blockscaled GEMM API with recipe `iq2_xs` and activation mode `a16`.

The same loader and compute paths accept `IQ2_XXS` (256 weights per 66-byte
block) and `Q8_0` (32 weights per 34-byte block), with `packing="ggml"`.
Q8_0 embedding tables retain their packed blocks and use b12x's prepared
embedding lookup to decode selected rows to BF16. Dense layers and LM heads
use the corresponding `iq2_xxs` or `q8_0` blockscaled recipe.
Q8_0 dense layers require K divisible by 32; Q8_0 expert hidden and intermediate
dimensions must be divisible by 128. Resident XXS storage stays at 66 bytes
per 256 weights; Q8_0 stays at 34 bytes per 32 weights.

`scripts/serve-super3-packed-spark.sh` selects
`nvidia/NVIDIA_Super3_5_VL_IQ2XXS-Packed`, including its XXS experts, Q8_0
embedding/latent projections/LM head, and NVFP4 layers. It prefers the cached,
validated snapshot; `MODEL_PATH` may select another local snapshot. Run it with:

```bash
./scripts/serve-super3-packed-spark.sh
```

The launcher serves `super3-packed` on port 8000 (`PORT` overrides it), enables
the checkpoint's custom configuration code, and uses CUDA graphs with b12x
autotuning enabled by default. Defaults are an 8192-token context, two concurrent sequences,
256-token prefill chunks, and a 2 GiB KV cache. Override these with
`MAX_MODEL_LEN`, `MAX_NUM_SEQS`, `MAX_NUM_BATCHED_TOKENS`, and
`KV_CACHE_MEMORY_BYTES`, respectively. Additional vLLM flags may be passed as
script arguments.
Expert parallelism, EPLB, and other IQ encodings are unsupported.

## EXL3 routed experts

The `exl3` quantization method serves MoE checkpoints whose routed experts
are stored in an EXL3 container: `exl3-manifest.json` plus one
`exl3-layer-NNNNN.safetensors` file per MoE layer in the model directory.
The text configuration declares it as:

```json
"quantization_config": {
  "quant_method": "exl3",
  "dense_format": "mxfp8",
  "exl3": {"manifest": "exl3-manifest.json"}
}
```

Each tensor-parallel rank reads a contiguous slot extent of every MoE layer,
aligned to the manifest's extent blocks and barriers, so the intermediate
width need not divide the tensor-parallel size and no padded expert payload
is allocated. Tensor-parallel sizes 2 through 24 are supported without
expert or data parallelism. Experts run with BF16 activations; dense layers
keep their serialized MXFP8 and BF16 formats.

## Qwen PLE table storage

Qwen4Exp and Qwen3.8-Flash-Next implement BF16, per-table FP8 E4M3, and
group-16 NVFP4 PLE embedding storage with b12x. The text configuration's
`ple_embedding_dtype` must match the checkpoint table weights. When omitted,
vLLM resolves it from the safetensors headers before allocating the table;
the activation `--dtype` does not select the table format.

BF16 tables default to disk offload (`io_uring`), reading only the batch's
selected rows before CUDA graph replay. FP8 and NVFP4 tables default to GPU
memory. Disk offload requires safetensors checkpoints and supports the
`safetensors`, `fastsafetensors`, `instanttensor`, and `b12x` loaders.

Explicit settings override these defaults, in descending precedence:

1. `--additional-config '{"ple_table_memory":"disk"}'` (`disk`, `ram`, or `device`).
2. `VLLM_PLE_TABLE_MEMORY` (`disk` or `ram`).
3. `VLLM_PLE_CPU_OFFLOAD` (`1` for CUDA-mapped host RAM, `0` for GPU memory).

## PCIe All-Reduce

The B12X communication backend provides single-node PCIe all-reduce for SM120
and SM121 GPUs. Tensor-parallel sizes 2, 4, 6, and 8 use an all-peer one-shot
algorithm. Tensor-parallel sizes 12 and 16 use a bounded-degree hierarchical
algorithm. Enable it with:

```bash
VLLM_ENABLE_PCIE_ALLREDUCE=1 \
VLLM_PCIE_ALLREDUCE_BACKEND=b12x \
vllm serve <model> --tensor-parallel-size <size>
```

The backend also fuses eligible one-shot all-reduces with residual addition and
RMSNorm through the vLLM compilation pass. Inputs rejected by the B12X size,
dtype, layout, or topology checks use the normal vLLM all-reduce path.

The default one-shot and fused-operation limits are both 84 KiB. Override them
with `VLLM_PCIE_ONESHOT_ALLREDUCE_MAX_SIZE` and
`VLLM_PCIE_ONESHOT_FUSED_ADD_RMS_NORM_MAX_SIZE`.

The lossless BF16 two-shot algorithm is disabled by default. Set
`VLLM_PCIE_TWOSHOT_ALLREDUCE_MAX_SIZE` to a byte size (for example, `768KB`)
to route eligible inputs above the one-shot ceiling through it.

For larger prefill collectives on all-peer topologies, the backend uses the
B12X DMA ring at or above `VLLM_PCIE_DMA_MIN_BYTES`, which defaults to 6 MiB.
This crossover is topology-dependent; set the variable to `off` when the DMA
ring has not been qualified against the fallback collective on the deployment
hardware. Inputs not accepted by an enabled B12X algorithm use the normal vLLM
all-reduce path. `VLLM_PCIE_DMA_FP8` selects an optional compressed DMA wire
format; leaving it unset preserves lossless transport.
